Bonsai-8B Model Analysis: Why is this actually fast?

Published Apr 2026 • ⏱ 15 min read

The PrismML team recently released their Bonsai family of models—1-bit quantized models with a compression ratio of 12x-14x. I searched for a complete breakdown of these models and what's actually happening inside them, but didn't find many resources. After reading through all available resources, code, and brainstorming with Claude, here's the breakdown of what I learned about these models and their inner workings.

The main theme of this post is to understand the quantization (1.125 bits, referred to as Q1_0 with g=128), why these models are fast, and the parameter breakdown (it's just Qwen3).

Bonsai vs BitNet

What is BitNet?

The first thing that came to my mind after seeing the Q1 quantization was Microsoft's BitNet models. Initially, I thought these Bonsai models would use the same method as BitNet, but they're actually different.

BitNet is a 1.58-bit LLM, where 1.58 actually represents 3 states: {-1, 0, 1}. A single bit can store 2 states, so 3 states require log₂(3) = 1.58 bits of information to represent optimally — that's information theory (Shannon's source coding theorem), not a literal extra bit. In practice, 4 ternary values are packed into one INT8 (since 3⁴ = 81 < 256), giving an amortized cost of 8/4 = 2 bits, which is close to the theoretical 1.58. Since systems don't have a native 1.58-bit datatype, these are packed into integer variants like INT8 or INT32.

However, BitNet is not entirely 1.58 bits—some components of the model use higher precision:

  • Activations: 8-bit (BitNet b1.0 / b1.58), 4-bit (b1.58 v2)
  • Weights are 1.58-bit quantized
  • Embeddings and output heads (which play a major role) are kept in full precision

How BitNet Computes — No Dequantization

All quantized weights have associated scales: activation scales for activations and weight scales for weights. For BitNet, each layer has a single scale value responsible for scaling the quantized values of the entire layer. (The actual smartness of Bonsai comes from here—we'll see this as we understand the approach.)

But here's the critical distinction: with proper kernels like bitnet.cpp, BitNet never dequantizes weights back to floating point. Instead, the entire matrix multiply stays as pure integer operations on {-1, 0, +1} values — essentially XNOR + popcount operations. The two scale values (one weight scale, one activation scale) are applied just once at the very end. This is why BitNet achieves both memory and compute savings.

Why Scales? Where Does the Speedup Come From?

Why scales? The answer is data movement. I briefly mention this in my intro to GPU programming (CPU vs GPU section). All of this is essentially optimizing for data movement. You can read more about this in the recent paper "Data Gravity and the Energy Limits of Computation" [1]. In short, data movement takes the majority of time as well as energy (power consumption).

When you use lower quantizations, you pack the data to save on all data movement overhead. For GGUF-based inference (which Bonsai uses), you later unpack and scale them when actual computation is about to happen, which incurs a small cost but is much less compared to what full-precision data movement would require. For BitNet with bitnet.cpp, you don't even unpack — you compute directly on packed bits.

This is also why you need specialized kernels to handle packing, unpacking, and scaling based on the specific device architecture—that's where the actual speedup and gains come from.

Enter Bonsai

I believe it's now clear what BitNet and this ternary quantization were doing and where the speedup came from. Let's see how Bonsai does this differently.

Bonsai models are quantized to Q1_0 (g=128) format, which has only two states: {-1, 1}. A group of 128 weights shares a single scale value. This is where things become interesting. Bonsai models apply this quantization to all layers and parameters, whereas BitNet retains higher precision values for activations, embeddings, etc.

Since they share a scale for a 128-weight block, it's possible to do this without compromising accuracy. Why? In a layer with 20,000 weights, the BitNet model would have only 3 unique values, but for the Bonsai model, the total unique values would be (20,000 // 128) × 2, which is approximately 312. This gives us more expressive power. This is actually very interesting because you're saving more memory while simultaneously increasing the expressive power of the model.

The 1.125 Bit Calculation

Where Does 1.125 Come From?

The "1.125 bit" number comes from a very specific hardware alignment choice. Bonsai groups 128 weights together and gives that entire group a single FP16 Scale. I did some research and learned that 128 is actually a standard from the GPTQ format, used for hardware-specific reasons—it's a sweet spot that makes things faster.

Each weight is 1 bit (sign), and we have one 16-bit (2 byte) scale factor for every 128 weights. The math looks like this:

Bit Cost Breakdown per Weight
1 bit → sign bit (the weight value itself: +1 or −1)
16 bits ÷ 128 → cost of the shared FP16 scale, amortized across 128 weights
1 + 0.125 = 1.125 bits / weight
1 bit (weight) + (16 bits (scale) / 128 weights) = 1 + 0.125 = 1.125 bits/weight

This extra 0.125 bits provides a massive boost in fidelity because it allows the model to handle local outliers in weight distribution. It's like having a volume knob for every tiny segment of the model instead of one master volume for the whole layer.

How Bonsai Actually Uses Scales

The Core Insight: Scale Applied Before Matmul

This is probably the most important implementation detail to understand. Unlike BitNet — where a single layer-wide constant scale can be pushed to after the matrix multiply — Bonsai's group scales must be applied before the matmul. Here's why.

The Linear Algebra Reason

A single constant scalar can always be factored out of a matrix multiply: (c × W) @ x = c × (W @ x). So BitNet can pull its one scale to the very end and keep the matmul pure integer. But Bonsai has 156 different scales across the weight matrix — you cannot factor out a varying quantity. Each group's scale must be applied to its group of weights before the multiply happens.

Why More Scales = More Expressiveness

Consider a layer with 20,000 weights. Group 47 might have large weights (scale ≈ 0.847), while group 112 has tiny weights (scale ≈ 0.073). Without group scales, a single global scale would crush the small weights — 0.03 ÷ 0.412 ≈ 0, information gone. With group scales, 0.11 ÷ 0.073 ≈ 1.5, which rounds to ±1 and the variation is preserved.

This is why Bonsai claims better accuracy than you'd expect at ~1.125 bits: it's 156 independent "volume knobs" instead of 1 master knob, at the cost of the matmul staying in FP16.

Under the Hood: GGUF Inspection

Architecture

I wanted to check the details in depth, so I inspected the GGUF file provided for actual numbers and model architecture. As they mention clearly, the Bonsai models use the Qwen3 architecture—the same vocab, layers, parameters, and everything else.

Size & Compression Numbers

Model Statistics

  • Total Parameter Values: 8,188,548,096 (~8.2B)
  • Model Stored Size: 1.15 GB
  • FP32-Equivalent Size: 32.75 GB (approx)
  • FP16 Equivalent Size: 16.38 GB (approx)
  • Model-wide Compression compared to FP32: 28.42x
  • Model-wide Compression compared to FP16: 14.2x

Storage Breakdown

Here's how much of this is 1-bit and 16-bit:

Non-scaled weights payload (sign bits only):

  • Bits: 8,188,239,872
  • Bytes: 1,023,529,984
  • Size: 1.023530 GB (0.953237 GiB)

Scaled payload (from tensor bytes minus sign bits):

  • Bits: 1,023,529,984
  • Bytes: 127,941,248
  • Size: 0.127941 GB (0.119155 GiB)

What These Numbers Tell Us

The sign bits make up ~88.9% of the total stored size, and the FP16 scales make up ~11.1%. This maps almost perfectly onto the 1 : 0.125 ratio from the bit calculation — the math checks out against the actual GGUF file contents.

Ending Note

I'm really excited about this model. I really want to know how they trained it. What I know for sure is that this training requires significant hard work in both the mathematical aspect as well as the engineering part. This is really genius work.

A few things worth knowing: it was trained from scratch natively in 1-bit — not post-training quantization of an existing model. The architecture blueprint is Qwen3 (not the weights — entirely fresh training). Interestingly, the mathematical foundation comes from Babak Hassibi's work at Caltech — the same person who co-invented the Optimal Brain Surgeon (OBS) in 1993, which is the theoretical ancestor of GPTQ. Training was done on Google TPU v4.
